# 节点表述规范

目的手段链中的每个节点都应表述一个单一、清晰的目的、子目的或手段。
节点在某条边上是目的还是手段，取决于它与相邻节点的关系，
不取决于句子本身的语法形式。

## 动宾与目标状态

优先使用动词加宾语，或“使对象达到某性质”的形式：

- `构造满足边界条件的数值解`
- `降低单步预测误差`
- `获得可用于判别的测量信号`
- `使用电化学方式削弱附着`

不要把分类标签直接作为节点，例如 `鲁棒性`、`模块化`、`注意力机制`。
应改为它在当前链中承担的目的或手段，例如 `提高输入分布变化下的预测稳定性`、
`使用注意力机制实现跨元素信息交互`。

## 明确具体

对象、性质和动作应尽可能指向可辨认的实体、属性或操作。
相近概念在后续展开不同，就必须区分表述。

例如，`降低序列长度`可能混淆输入 token 数、参与计算的查询数和键数，
应写出实际被改变的量。

## 原子化

一个节点只放一个目的或手段，不暗含多层链条、因果解释或并列关系。

- 不写 `用缓存降低延迟`，可拆为 `降低响应延迟` 与 `使用缓存`
- 不写 `收集数据并训练模型`，应拆为两个同级或相继节点
- 不把方案 A 与方案 B 写在同一节点，应使用 Or 子节点

可保留对当前语境不可缺少的条件或阶段限定，例如
`（推理阶段）降低显存占用`。限定语不能暗含另一条目的手段关系。

## 清楚且可讨论

避免 `设计得更好`、`方案合理`、`效果优秀` 等没有明确判断对象的表述。
改为可继续分析的目标状态或操作，例如 `降低推理时间`、
`使输出满足守恒约束`。

目的通常宜写成正向、可操作的转变，如 `降低误差`、`提高吞吐量`、
`避免碰撞`。不必为了形式而把自然的目的表达改成不通顺的否定句。

## 技术符号与检查

数学符号在比纯文字更准确、简洁时可以使用，并在首次出现时说明含义。
复查节点时，重点检查：

1. 是否能读成一个单一目的或手段
2. 是否混入了 `导致`、`为了`、`并且`、`或` 等隐藏关系
3. 相邻节点是否因对象、条件或阶段不同而实际不等价
4. 去掉多余修饰后，节点含义是否更清楚
