# 使用场景与展开宽度

本文件帮助选择目的手段链的展开范围。所有场景仍遵循主 Skill 的
逐节点流程、直接关系检查、共享手段处理和树形输出规则。

## 1. 从头设计或探索替代方案

**目的**：围绕给定根本目的，提出多类可行的系统方案。

**展开策略**：

- 根本目的表达待实现的正向功能，不表达对原系统缺点的局部修补
- 在方案大类层积极展开 Or 分支
- 先区分工作原理、对象类型或关键机制，再深入具体实现
- 不因当前缺乏某项资源而删除方案，只降低其优先级
- 资源、成本、部署条件等在具体手段下作为实施条件或子手段分析
- 最终由用户基于资源、成本、风险和效果选择方案

适用于新系统设计，也适用于通过新系统替换旧系统。

## 2. 替换或重构已有系统

**目的**：不在原系统内部修补，而是重做它本应实现的功能。

**展开策略**：

1. 识别旧系统本来要达成的根本目的
2. 将该目的作为新手段链的根，不把旧系统结构当成必经路径
3. 把旧系统视为现有方案之一，必要时在同层与替代方案比较
4. 若不清楚旧系统为何失败，可单独记录其失败机制，
   但不把这类机制解释混入本树

这样得到的是替代性设计空间，而不是旧系统的局部修复清单。
若用户要保留原系统并在其内部解决缺点，不属于本场景。

## 3. 论文、算法或既有方案的结构解读

**目的**：说明一个已知方案的手段如何逐层服务于其目的，检查是否跳步，
或定位其真正的创新位置。

**展开策略**：

- 优先还原论文或方案实际采用的路径
- 除非用户要求比较或发散，不必为每个目的补齐大量未采用的 Or 方案
- 可以在关键节点简要标出相邻方案大类，用于说明该方法的选择意义
- 区分“该方法实际做了什么”和“还可能怎么做”，避免把后者误写成原方法结构
- 若论文包含对旧方法缺点的解释，将其视为背景说明，
  不混入目的手段链

论文通常不会显式写出所有中间手段。
分析结果默认是分析者根据材料与领域知识还原的完整结构，
可以补出作者省略的桥接层，无需逐节点标注是否为作者原话。
但补出的桥接层必须与方案实际结构一致，
不得把方案未采用的替代手段误写成其组成部分。

## 4. 功能测试与设计评审

**目的**：检查一个既有设计是否真正具备实现目标的关键手段，或决定先验证什么。

**展开策略**：

- 从待验证的目标功能向下拆关键前提和子手段
- 优先展开最容易验证、最可能决定成败的节点
- 测试行为本身可作为对某个前提性质的评判手段
- 发现某手段未能实现时，记录该事实，
  但不在本树中继续追溯其失败机制

该场景的树通常较窄，重点是发现设计假设和测试顺序，不是生成完整方案库。

## 5. 领域话题框架或知识组织

**目的**：围绕开放目的与开放手段，组织一个领域中的方法关系。

**展开策略**：

- 以较稳定、可迁移的目的和方案大类为主，避免陷入某篇论文的实现细节
- 同一手段服务多个目的时，优先抽成独立子树并在各处回指
- 不必一次写尽全部细节，可先建立高层骨架，再逐步补全高价值分支
- 注意一个手段在不同目的下可能扮演不同角色，不因名称相同就强行合并

此场景的结果可作为笔记组织骨架，但是否合并到具体笔记由用户决定。
