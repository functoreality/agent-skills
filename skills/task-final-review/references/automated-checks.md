# 自动化与功能检查

在产物存在可重复判定的约束，或程序行为需要验证时查阅。
选择能回答当前问题的方法，无需覆盖下列所有类型。

## 先明确检查能证明什么

从有效需求中提取可观察条件，例如文件能解析、记录不丢失、
某输入产生预期输出、失败时返回明确错误。
预期值应来自要求、可信样例、独立计算或已知正确的实现，
不能直接抄待测产物的结果作为答案。

优先使用项目已有的校验器、构建流程和测试。
确认命令覆盖的目录、配置、输入和生成物就是本次交付范围，
旧报告或不相关测试通过不能证明本次改动正确。

## 格式、结构与一致性

- 用格式对应的解析器或校验器检查语法、字段和结构约束。
  对有 schema、模板或项目规范的产物，按实际适用版本核对。
- 检查产物中的内部链接、资源路径、跨文件引用和必要附件是否完整。
  文件存在还不代表引用内容正确，重要引用仍需核对语义。
- 对文件移动、配置调整等操作，核对目标位置、实际配置或生效后的状态。
  命令退出成功不等于预期状态已经实现。
- 对数据转换、整理或迁移，按需求核对记录数、标识、重复与缺失值，
  以及处理前后应保持不变的信息。总数相同仍可能存在错配或遗漏。
- 搜索可快速定位占位符、禁止模式或可疑项，
  但命中需要结合语境判断，未命中也不能证明内容质量合格。

检查规则取自本任务的真实约束，不把某种写作风格或固定阈值套用到全部产物。

## 程序与功能

按变化涉及的行为选构建、类型检查、单元测试、集成测试或实际运行。
这些手段覆盖不同问题，构建成功不代表功能正确。
关注用户可观察的输入输出、状态变化及必要的失败处理，
避免只验证内部函数被调用或实现细节与当前代码一致。

典型选择依据：

- 修改了一个明确行为：验证该行为及受影响的相邻路径。
- 修复了可复现缺陷：保留原始触发条件，确认修订后不再出现，
  必要时增加可防止同类回归的测试。
- 改动影响多个组件或输入输出衔接：检查真实的组合路径，
  不能只依赖各组件分别通过测试。
- 涉及错误输入、边界值或兼容性：选择与任务相关的代表性情形，
  不机械穷举所有可能输入。

对可逆、低影响的微小修改，不为形式完整而新增测试。
对外部状态的写入，应沿用任务已有授权和测试环境，
不要为了验证而直接执行生产发布或其他未授权动作。

## 数值、公式与数据结果

对决定结论的合计、比例、单位、公式或转换，
从原始输入独立重算，必要时用简单可手工核对的样例交叉检查。
留意量纲、分母、索引、精度和缺失值处理是否符合实际含义。
验证合理的不变量，例如拆分后总量守恒，
但不要假设本任务并不保证成立的不变量。

抽样应覆盖不同类型或容易出错的分支，并说明抽样范围。
涉及关键结论、规模允许且约束可自动化时，优先核对全部相关数据。
不能把抽查若干行表述为全量正确。

## 是否新增检查脚本

只有重复执行、规则清楚或人工核对易漏时，才值得写可复用脚本。
单次简单核对可以直接使用现有工具，不必建立通用检查框架。

新脚本应在已知符合和已知不符合规则的样例上运行，
确认既能放行有效产物，也能发现目标缺陷。
说明它的检查范围，不能把“脚本通过”扩大解释为“整体质量通过”。

## 结果处理

保留可追溯的命令、输入版本、退出状态和关键输出，按任务规模从简。
检查器没有实际执行、读错文件或只扫描了空目录，都不能算通过。
发现失败后区分真实缺陷、规则误报、工具限制与环境故障，分别处理。
修订后只重做受影响的检查，确认报告对应最终版本。
