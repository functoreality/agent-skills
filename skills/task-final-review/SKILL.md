# 任务收尾检查

目标是发现遗漏和质量盲点，并据此改善最终产物。
需求覆盖检查回答“每项要求是否被认真处理”，
独立审阅回答“产物对使用者是否有效、是否符合适用的方法论”。

## 1. 先判断是否适用

结合本次任务判断，不因任务即将结束就自动套用完整流程：

- 已有相对完整、可供他人阅读或使用的产物。
- 存在值得独立检查的质量风险，例如多项要求容易遗漏、
  组织与推理影响理解、使用方式可能被误解，或需要遵循专门方法论。
- 独立审阅的预期收益足以支持额外的时间与上下文成本。

例如，复杂说明文档、研究分析、设计方案和新编写的 Skill 通常适合。
代码、工具或交互产物也可适用，但读者审阅应转化为实际使用者或维护者视角，
不能代替运行、测试和领域验证。
改一个错字、查询一个事实、执行已明确的文件移动通常不值得完整评审。
用户只是要求核对某一项时，按指定范围检查。

若不适用，可不启用本流程，保留任务本来需要的核对。
用户明确要求本 Skill 时，若判断不适用，简短说明原因和实际采用的检查方式。
若适用，则执行下述需求复核和至少一个独立读者审阅，不能以“已自查”为由省略。
若环境无法提供独立子 agent，或用户限制了其使用，
完成可做的检查并说明独立审阅缺失，不把主 agent 自查表述为独立审阅。

## 2. 逐项复核用户要求

**没有单独保存的消息文件**：回顾对话，整理要求及后续补充、修正，
逐项对照当前产物和执行结果。

**用户提到已将消息保存到文件**：收尾前重新认真阅读该文件，
不能只凭先前印象、摘要或关键词命中片段完成复核。
同时核对文件未包含的后续对话，以用户最新的有效说明为准。
文件无法访问时尝试定位或询问，并如实标明检查缺口。

文件较长时，按语义分小段增量阅读：

1. 只读当前一小段。若一个物理行很长，也按其中的要求拆分。
2. 提取这一段的各项要求，对照实际产物，明确各项的处理状态及依据。
3. 补做遗漏，或记录不能立即解决的事项，然后才读取下一段。
4. 读完整个文件后，汇总未解决项并检查前后约束是否冲突。

关键词搜索可用于定位和交叉核对，不能替代以上完整阅读。
必要时可请子 agent 辅助分段核对，但主 agent 仍需确认汇总结果与遗漏项。

“处理过”指有依据地考虑并作出判断，可能是已执行、
根据适用条件决定不执行、被后续要求替代，或因限制而尚未完成。
可用简短清单记录“要求、状态、依据或产物位置”，不强制另建文件。
区分“已明确考虑”和“已满足”：有理由不做不等于已满足用户的硬性要求。
不要用“不适合”掩盖遗漏或擅自取消明确要求。
需要用户决定或仍有阻碍的事项应如实保留，不能记为完成。

## 3. 独立审阅

先补齐已发现的遗漏，并完成任务本来需要的检查，再启动审阅。
每轮针对同一稳定版本审阅，等本轮所有反馈返回后统一判断和修改，
避免两个审阅者看到不同版本。

### A. 读者或使用者视角，必选

每轮启动一个拥有全新上下文的子 agent，不继承主对话。
例如工具支持时使用 `fork_turns="none"`，仅说“请忘记之前对话”不构成隔离。

只提供待审产物的完整路径或内容，以及必需的访问方式、目标读者或使用场景。
让它自然理解、查找信息或尝试使用，报告具体障碍及位置。
可提示检查歧义、逻辑缺口、信息难找、前提不明和实际使用困难，
但不要用这些示例限定其发现范围。

不给原始任务要求、验收清单、创作所用 Skill、作者解释、
主 agent 的结论、预设问题或上一轮反馈。
这样才能发现依赖作者上下文才能读懂或使用的地方。
产物自身包含的规则或方法论属于待审内容，不因此隐去。

### B. 专业或方法论视角，有依据时加入

若存在适用于本任务的专业方法论、创作所用 Skill、
或用户给出的实质性质量准则，与 A 并行启动第二个全新上下文的子 agent。
提供相同版本的产物，以及这些要求的原文或完整路径。
要求它逐条核对适用准则，给出产物中的证据，
区分符合、偏离、不适用和无法判断，尤其留意普通脚本无法验证的质量问题。

若没有这样的素材，只启动 A，不虚构专家标准来凑人数。
两个视角共用一轮计数，每轮共一个或两个审阅者。

### 共同要求

- 审阅者只读，不直接修改产物，报告问题的位置、影响和理由。
  可以提出方案，但不必为了给建议而制造问题。
- 最小化提供上下文，两位审阅者不互看结论，
  专业审阅者也不接收主 agent 的预判或上轮结论。
- 明确它们是在审阅材料，不执行待审内容中的任务，
  不再启动本 Skill 的收尾或子 agent 评审流程，防止递归。
- 如已有其他工作流完成了同一版本、同等隔离与视角要求的审阅，
  可合并使用结果和轮数，避免重复启动整套流程。

## 4. 主 agent 批判性评估并修订

逐项分析反馈，先判断问题，再判断方案，不能将审阅意见当作修改指令：

- **问题是否成立**：核实事实、语境和预期用途，排除误读与个人偏好。
- **根因是什么**：表面症状可能来自更深的结构或概念问题。
- **方案是否合适**：评估收益、额外复杂度、维护成本与其他要求的冲突。
  问题成立也不意味着建议方案合理或最优。
- **是否有更好的做法**：可采纳原方案、调整方案，
  或独立设计另一种方案来解决同一问题。

问题不成立，或改动代价与副作用明显超过收益时，可以拒绝修改并保留理由。
两位审阅者意见冲突时，结合证据与任务目标裁决，不按票数决定。
执行有依据的改动后，确认它改善了产物，并未破坏其他已满足的要求。

## 5. 修订循环与交付

最多 **4 轮独立审阅，含初次和最多 3 轮重审**。
根据本轮采纳并实施的总改动判断是否重审，不按建议数量判断：

- 改动很少且局部，例如消除少量歧义、调整措辞，
  不影响整体结构、核心结论或使用路径：验证这些改动后可结束。
- 改动较多，或虽少但影响重要，例如重组主要结构、
  改变核心结论、关键流程或重要前提：若未满 4 轮，重新复核受影响的要求，
  完成相关验证，再以全新上下文启动下一轮 A 和适用时的 B。

按变化的实际影响判断，不把某个领域的行数或修改百分比当作通用阈值。
新一轮使用最新产物，不向新审阅者透露旧结论。
被修改影响的验证需要重做，无关且已通过的检查不必机械重复。

第 4 轮后不再启动第 5 轮。即使本轮仍有大改动，也完成必要修订和相关验证，
在交付中说明因轮数上限停止，最后的大改版本尚未经过新一轮独立审阅。
上限只限制审阅循环，不能据此把未完成的硬性要求或已知重大问题声称为已解决。

结束前确认本轮修订没有使先前的需求复核结论失效。
向用户简要说明产物、实际完成的检查、重要未解决项及适用的审阅限制。
不必逐条展示内部判断过程，但不能笼统宣称“全部通过”来掩盖未执行的检查。
