# 阶段一需求核对

采用 Task Final Review 的需求覆盖、内容核对和行为试用要求。
计划检查由主 Agent 执行，本轮不另设审核 Agent。
完整阅读 prompt.txt 后，按语义段核对如下。

| 需求段 | 要求 | 计划处理 |
|---|---|---|
| 1–20 行 | 两个 Skill，方法组合，先验生成与后验解释、失败 | plan 评估口径及 solver 路由 |
| 21–40 行 | 案例汇总、方法边界、Skill 补充、RA | plan 阶段五与 solver 分开归因 |
| 41–62 行 | 全题与答案追溯、少量试点、队列、调整留痕 | extraction 协议，冻结后揭答 |
| 63–80 行 | 先计划与索引，再 3 题，审核后才全量 | plan 阶段一到四与明确停止点 |
| 81–96 行 | 双汇总、方法说明、Git、小提交与收尾核验 | plan 阶段五、文件组织与本记录 |

## 执行决定

- 三个提取 Agent 是资料整理分工，不承担盲解，不启动自己的 Agent。
- 试点解题使用另三个全新上下文，各一题，先保存候选再揭答。
- 不直接调整 Skill，不越过用户的第三步审核停止点。
- 无编号实例纳入索引，题干或答案不可用单独保留，不编造解法。
- 先验候选不能仅靠宽泛方向命中，记忆污染与方法推导证据分别记录。
- 后验调整只作为改进假说，单次未解不推断方法完全不适用。
- 不需要外部账号或用户背景，原文和本地 Skill 均可读取。

## 计划核验结果

需求覆盖自查未发现需用户补充才能开展前三步的缺失信息。
检验方法增加的“候选冻结”“A-memory”“U”用于维护用户要求的区分，
不改变用户的 A/B/C 主问题。
阶段一产物为 ../planning/plan.md 与 ../protocols/solver.md。
阶段三和最终阶段五仍需针对实际产物再次核验。
