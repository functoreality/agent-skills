```markdown

- 已知方案或材料范围：……
```

- 方案地图：允许大类 `暂缓`，但不得把它写成已完成方案。
- 设计或替换：至少应有一条高价值路径闭合到约定粒度。

只有当多个要求共同构成一个不可拆的功能定义时才合并为一个根。队列与收尾检查也按每个根分别执行。

3. 当前树丢失了“这组边在回答什么问题”的语义

[步骤 3.3](/home/yzh/Documents/projects/agent-skills/skills/purpose-means-analysis/SKILL.md:201) 很好地规定了四种展开轴：条件、方案空间、已选方案细化、测量判别；但这一判断不会落入最终树中。

因果链所有边本质上都是“原因”，可以只记录 And／Or。目的手段链却至少混有“必要条件”“替代路径”“方案逐层限定”“实施细化”几种不同关系。仅凭缩进和 And／Or，后续读者很难判断一组子节点是共同必需条件，还是某个方案的组成步骤。

建议使用轻量级的父节点标记，而不是给节点强加永久类型，例如：

```markdown
* 获得可用于预报的准确模型：条件拆解
* 构造映射：方案空间；or
* 采用神经网络表示映射：实施细化
```

这样保持现有“同组兄弟只用一个关系轴”的原则，也让结果文件本身可读、可复查。

4. `末端` 的终止依据还不够可操作

当前 [步骤 3.5](/home/yzh/Documents/projects/agent-skills/skills/purpose-means-analysis/SKILL.md:291) 已区分“末端”和“暂缓”，这是正确修复；但“达到粒度、自然原理、外部标准或边界”仍被并列为末端理由。

这些对于后续使用的意义不同。例如“使用已给定的外部服务”可以是本轮设计边界，“遵守某标准”却通常仍需要继续拆成具体实现手段。否则树容易把约束、未分析的黑箱和可实际采用的手段都误读为同一种完成状态。

建议补一条终止判定：

> `末端` 必须是已接受的实现粒度边界、外部已提供能力，或继续展开不会改变本次设计结论的基本原理。缺少信息、资源、用户选择或仍需制定实现路径的节点一律标为 `暂缓`，不以“外部标准／边界”笼统终止。

这不把可实施性、资源权衡或因果改进塞回手段链，只是让“树已经完成到哪里”可被可靠判断。

总体上，我的判断是：当前 Skill 的逐节点展开、优先队列、局部验证与复盘主骨架已经成立；但应补一个“分析约定 + 模式化收尾”的外层结构，并完善多根目的、边语义和终止判定。这样才是从因果链的单一根因树，真正迁移为适合设计空间的目的手段分析框架。

这些是四个相互关联但影响较大的结构改动。按复盘流程，我先不直接编辑。你若认可，我建议先实施第 1、2 项作为同一次结构重构，再决定第 3 项的标记是否要强制写入每个父节点，还是只在语义不明显时使用。
